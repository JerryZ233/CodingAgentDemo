# 分层 Memory Harness 实施计划

本文件保存 2026-10-20 与用户确认的设计，供不同 session 接续实施。实际完成情况见 [MEMORY_PROGRESS.md](MEMORY_PROGRESS.md)。

## 目标与调用边界

三层记忆分别为全局长期记忆、项目长期记忆、项目历史。原始会话完整保留，不作为额外的记忆层。每次编码模型输入包含基础提示、工具说明、精简的全局/项目长期记忆、当前会话连续摘要，以及当前会话尚未压缩的全部近期消息。其他历史通过工具按需查找。

`SessionService` 继续负责生命周期、前台运行准入、持久化及取消；`Context` 保留原始消息，不直接读写记忆文件或调用整理模型；后续 `MemoryHarness` 协调输入组装、归档和提炼。

## 已锁定的决策

- Git 项目以当前 worktree 的根目录为边界；子目录会话共享项目记忆，普通文件工具仍以会话工作目录为边界。非 Git 目录以真实工作目录为项目根。
- 全局文件在 `~/.coding-agent/global/MEMORY.md`；项目文件在 `<projectRoot>/.coding-agent/MEMORY.md`，项目长期文件可以提交 Git。
- 原始会话保持既有 `session-dir`。项目历史、来源、候选、备份和事务信息放 `.coding-agent/local/`；通过该目录上级的 `.gitignore` 忽略 `local/`，不自动 git add/commit。
- 长期文件采用带稳定条目 ID 的 Markdown。用户可编辑正文；来源详情不写入共享正文。
- 项目知识有充分来源时自动更新。全局更新必须获得用户明确批准，不从项目行为推断全局偏好。
- 新证据明确证明迁移/纠正时更新旧条目；其余冲突保留旧值并询问用户。
- 当前项目空闲时展示一条候选，支持“保留旧的”等自然语言回复；回复只作用于已展示候选。后台新增候选不能切换回复目标。全局批准必须明确作用域。
- 整理复用当前模型/客户端，使用无工具请求。第一版估算 Token，不增加 tokenizer 或向量数据库。
- 自动预算压缩；新增 history 达到阈值后，编码结果已保存的前台轮末串行提炼。维护失败不把已完成编码标为失败。
- 首次启动立即后台整理当前 session-dir 中未整理的旧会话。后续只在 dirty 且距离上次成功整理至少 24 小时时处理，间隔可配置。
- 后台自身最多一个任务，可与前台并发调用模型；不整理正在前台修改的同一会话。提交前检查内容与摘要状态版本，过期快照不得覆盖新状态。
- 短时文件锁和版本检查解决跨进程写入冲突，冲突拒绝写入并可重试，不自动合并。模型请求期间不持文件锁。
- 退出只保存/取消，不启动新的整理。保持现有五秒关闭预算和可重试关闭。
- 项目只读时允许读取，不自动转存；需要压缩却无法安全持久化时暂停本轮。
- 第一版保留全部原始会话、已提炼 history 和修改前版本，不自动清理。
- 压缩失败但完整输入能放下时继续；否则暂停，不静默截掉早期约束。

## 数据与配置合同

### 会话版本 2

- `Message.id` 为内部稳定 UUID，复制/内容替换保留，模型协议不发送。
- 版本 1 消息 ID 根据会话 ID 和原始序号确定性生成；读取不写文件，保存时升级为版本 2。
- `contentRevision` 只随原始对话变更递增；提示、标题、运行状态和整理元数据变化不增加它。
- `SessionMemoryState` 保存 `lastOrganizedRevision`、`lastOrganizedAt` 与 `CompressionState`。
- `dirty = contentRevision > lastOrganizedRevision`。首次未整理立即有资格，之后需要同时满足 dirty 和最小间隔。失败/取消不推进成功标记。
- `CompressionState` 保存覆盖到的消息 ID、归档 ID、连续摘要、独立版本。覆盖边界必须存在且不拆开工具调用/结果块。
- 后台资格还必须检查有消息、无前台写入，以及错误退避；前台预算压缩不受维护间隔限制。

### 归档与长期文件

历史最小信息：`id`、`operationId`、`sessionId`、`sourceRevision`、`coveredMessageIds`、`previousSummaryId`、`archiveSummary`、`continuationSummary`、`keywords`、`sourceRefs`、`createdAt`、`promptVersion`。

`archiveSummary` 只描述新增区间供检索/提炼；`continuationSummary` 合并旧连续摘要和新增区间，供当前会话继续运行。不得反复总结整个 history 文件。

归档提交顺序：已保存原始消息 → 写事务信息 → 追加归档 → 保存会话摘要/边界/整理标记 → 写提交记录。只有已提交归档可被检索。恢复时依会话引用补全提交，或忽略孤立未提交项；操作 ID 去重。

长期操作限定为新增、更新、失效、忽略。检查来源、作用域、预算、条目 ID 和文件内容版本后写入；保存旧版本和恢复日志。格式损坏停止自动修改并提示。新克隆只含 `MEMORY.md` 时仍可读取，来源标为本地不可用。

### 默认设置

```yaml
memory:
  enabled: false                  # 阶段 8 集成验收后改为 true
  context_window_tokens: 32768
  safety_margin_tokens: 2048
  compact_trigger_ratio: 0.80
  compact_target_ratio: 0.60
  global_budget_tokens: 1024
  project_budget_tokens: 3072
  summary_budget_tokens: 1200
  retain_recent_blocks: 2
  consolidation:
    enabled: true
    new_history_threshold: 5
    batch_size: 10
  maintenance:
    enabled: true
    min_interval_hours: 24
    scan_interval_seconds: 60
```

所有字段支持同路径大写、点号改下划线的环境变量，例如 `MEMORY_MAINTENANCE_MIN_INTERVAL_HOURS`。优先级保持环境变量 > 本地 YAML > 公共 YAML > 默认值。总输入预算扣除安全余量和 `llm.max_tokens`，并计入系统提示、工具 schema、消息封装和工具参数。

## 分阶段实施与验收

| 阶段 | 实现内容 | 核心验收 |
| --- | --- | --- |
| 0 | 工作区/调用链基线、`MemoryConfig`、记录进度 | 既有构造入口兼容，默认关闭，不产生后台或模型请求 |
| 1 | 稳定消息 ID、v1/v2 编解码、内容版本、恢复、项目定位 | 老文件可读，ID 稳定；恢复只递增真实修复内容；子目录共享/worktree 隔离 |
| 2 | Markdown 条目、history、本地版本、锁、原子替换和可恢复提交 | 每个提交步骤中断均无丢失/重复；未提交项不可见；冲突拒绝过期写入 |
| 3 | 协议块构建、Token 估算、统一输入组装、请求前钩子、受阻结果 | 全部输入计预算；未归档消息不静默丢弃；不可拆块超限可解释 |
| 4 | 无工具结构化摘要、增量压缩、连续摘要、请求用途 | 多次压缩保留约束/未解决问题；取消/失败不推进状态 |
| 5 | 历史搜索/读取服务和工具 | 新会话按需回忆，同项目隔离，有界结果，不增加默认输入 |
| 6 | 增量长期提炼、即时提案、持久候选、自然语言裁决 | 项目不升级全局；冲突询问；重复操作去重；模糊回复不写入 |
| 7 | 首次回填、24h+dirty 调度、轮末阈值提炼、并发提交/取消/关闭 | 时间边界正确；整理不制造 dirty；后台不能覆盖前台，维护结果独立 |
| 8 | CLI/日志/用量、隔离评测、迁移和恢复文档、默认启用 | 全部本地回归及专用记忆场景通过；统计覆盖后台/重试/缺失 usage |

### 后续实现要点

- 阶段 2 先完成可靠存取，不接入模型。存储抽象应能注入目录和故障点，不访问真实用户记忆目录进行测试。
- 阶段 3 Token 估算采用统一可替换算法：ASCII 约三字符一个 Token，非 ASCII 按码点计，并补结构开销。实际 usage 仅观测，不自动调整配置。
- 阶段 4 默认保留最近两个完整块和当前未回答用户消息。分批压缩，不穿过未完成工具块。JSON 非法最多修复一次；整理不占编码迭代次数，不执行模型返回的工具。
- 请求用途为 `AGENT`、`COMPACTION`、`CONSOLIDATION`，扩展现有 `LLMClient`/`RequestAttempt` 的兼容入口。
- 阶段 5 使用关键词/文本匹配；中文片段、英文词项；时间只同分排序。`memory_search` 默认 5 条、最多 10 条，`memory_read` 有界读取。宿主注入项目身份，不接受模型任意项目路径。
- 阶段 6 以已提交 history ID 记录已处理项，不能只用时间戳；每批有新增/更新/失效/忽略或持久候选的明确结果，提交成功后推进。保留所有历史。
- 工具为 `memory_propose`、`memory_resolve_latest`。后者宿主绑定已展示候选和用户来源，不接受模型切换目标。备用命令提供 show/search/compact/consolidate/pending/approve/resolve。
- 阶段 7 独立后台执行器每 60 秒发现会话；短时协调提交同时检查内存和磁盘版本；对同项目提炼批次做进程内预约。失败退避 5 分钟起、最多 1 小时，与成功时间分开。
- 只在当前项目空闲时展示其冲突；其他项目候选等切换后再显示。非交互入口持久保存候选，不等待输入。
- 阶段 8 当前编码评测显式关闭记忆、使用隔离目录以保持可比性。专用记忆评测覆盖早期约束、多会话继承、检索、项目隔离、前后台冲突和崩溃恢复。

## 测试和交接规则

普通测试可在开发中正常运行，包括 `src/test`、Gradle 单元/集成测试、本地 Python 测试，以及不调用真实模型的 Docker 测试和 Harbor 离线验证（oracle、initial）。只有调用真实模型 API 的测试需要用户显式指示；“跑一次harbor测试”默认授权一次 agent 模式真实模型评测，无需再次确认，也不自动重跑。以根目录 `AGENTS.md` 为准。

每阶段记录实际代码、测试结果、已知问题和下一阶段，不把“编译通过”写成“测试通过”。不同 session 先读取本文件、进度文件及 git diff，再从下一未完成阶段接续。不要覆盖用户已有改动，不自动提交用户的文件。
