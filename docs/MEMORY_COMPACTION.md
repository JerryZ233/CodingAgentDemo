# 自动压缩与连续摘要（阶段 4）

`memory.enabled` 仍默认关闭。开启后，前台模型请求准备阶段会在达到触发阈值时自动整理较早消息。阶段 5 已提供 [历史检索工具](MEMORY_RETRIEVAL.md)；当前不执行长期知识提炼或旧会话后台回填。

## 运行流程

```text
完整原始消息已经保存
→ 校验当前摘要与历史提交链
→ 估算完整编码请求
→ 达到触发阈值后，选择较早完整块
→ 无工具摘要请求（必要时分片）
→ 校验结构、来源、预算和实际压缩收益
→ 归档事务 + 会话 CAS
→ 更新同一个运行中 Context 所属的 Session 元数据
→ 重新估算，必要时继续下一批
→ 发送编码请求
```

只有开启记忆才走此链路。退出不触发新整理，摘要请求不占编码 `maxIterations`。CLI 仅展示整理开始、保存和失败提示，不展示内部摘要响应。

## 选择范围

`CompactionPlanner` 选择尚未压缩消息的连续前缀，保留 `retain_recent_blocks` 指定的最近完整协议块和当前最新用户请求。当前用户请求之后的工具观察也保留，不能通过跨越该用户消息来压缩。

每批约限制在输入预算的一半，避免一次归档处理整个积累历史；若单个旧块本身过大，则完整选择该块，由整理模型分片读取。先于大块的小消息不会使计划停在无法抵消摘要开销的过小批次。

触发后尽量降到 `compact_target_ratio`。若可压缩前缀已用尽，但完整请求仍满足硬预算，可以继续；当前受保护内容本身超限时则暂停，不删除或截掉它。第一版不会为满足目标比例而压缩当前用户要求。

## 摘要模型

`MemoryModel` 复用当前 `LLMClient`、模型参数和输出限制，不传工具 schema。提示版本为 `compaction-v1`，不使用 AgentLoop 执行整理响应。

响应严格要求：

```json
{
  "archiveSummary": "本批新增消息的归档摘要",
  "continuationSummary": {
    "constraints": [],
    "decisions": [],
    "completed": [],
    "currentState": [],
    "failedAttempts": [],
    "unresolved": []
  },
  "keywords": [],
  "sourceRefs": []
}
```

数组只允许非空字符串，空数组允许；连续摘要整体必须非空。拒绝多余字段、重复键、非严格 JSON、尾随文本、错误来源、过深结构、超预算摘要和工具调用。`sourceRefs` 只能引用已经提供的本批来源消息 ID；关键词最多 20 条。

连续摘要按固定小节渲染，预算包含发送给编码模型时的背景标签和消息开销。归档摘要单独受摘要预算限制。输出不合法时只额外请求修复一次；修复请求不附带任意长的坏输出。API 错误由既有重试策略处理，不再作为格式错误重试。

超长消息以带原始消息 ID 和字符偏移的片段提供，Unicode 代理对不会被切开。每次请求按实际渲染内容估算，预留修复提示空间。下一片携带上一片累积的连续摘要和本批归档摘要；整批成功前，部分消息不写成已覆盖状态。原始完整消息始终留在会话里。

## 提交、恢复和取消

`SessionArchiveCoordinator` 负责运行时接入：

- 提交前验证内存快照仍匹配生成摘要时的状态，磁盘写入使用 `compareAndSave`。
- 成功后只更新 Session 的摘要状态、时间和已保存快照，不替换 AgentLoop 正在使用的 Context。
- 归档保存会话检查点后、history 提交标记写入失败时，重新读取自己的检查点，确认来源和运行未变化，再同步内存并修补提交标记。
- 外部进程修改的内容或其他摘要不能被当成本次成功结果采用；报告存储冲突，保留本地未保存状态。
- 开启记忆的普通后续检查点也使用最近已保存快照做 CAS，防止最终保存覆盖新摘要或其他进程修改。自定义仓库必须实现条件保存。
- 请求前发现本会话引用尚未完成提交的历史时，只恢复本会话的提交标记再重新验证，不恢复或修改其他会话，不重放工具。

模型请求与文件锁不重叠。取消信号在摘要请求前后、各片之间和提交前检查。提交一旦被接纳，短文件事务完成并保留真实结果；提交之后发生取消不会回滚已落盘摘要。未提交的部分片段和非法输出不会推进整理标记。

摘要或提交前写入失败时，只有重新验证后的完整输入仍满足预算才允许继续。否则返回 `CONTEXT_BLOCKED`（摘要失败时原因 `COMPACTION_FAILED`），保留原始消息和最后成功的摘要。

## 请求用途与验证

`LLMClient` 增加带 `RequestPurpose` 的兼容入口，取值 `AGENT`、`COMPACTION`、`CONSOLIDATION`。普通调用默认 `AGENT`，整理及格式修复使用 `COMPACTION`。用途保存在每次 `RequestAttempt` 中，覆盖内部重试；不写入模型 API 请求体，也不保存在共享客户端的可变“当前用途”字段中。现有累计用量继续包含这些实际请求。

离线测试覆盖多批次与跨重启、工具循环内触发、超长消息分片、严格 JSON 和修复次数、无工具整理、输入能否安全回退、取消、会话检查点后的中断恢复和外部写入冲突。不得自动运行真实模型评测；授权规则见根目录 `AGENTS.md`。
